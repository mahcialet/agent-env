# 品質と検証

[英語版（翻訳元）](QUALITY.md)

変更を検証するときは、まず共通の検査コマンドを使い、変更する動作に応じて実際の実行環境を使うテストも選びます。
以下では、検査の実行方法、確認する動作、その結果から判断できる範囲を説明します。
実行記録が証明するのは、テストしたリビジョンと環境での結果に限ります。
必要なツールがないことやクロスビルドの成功を、実際のOS上での受け入れ検証の完了として扱いません。


以下の用語は、検査の対象と証拠の強さを区別するために使います。

| 用語 | この文書での意味 |
| --- | --- |
| ハーネス（harness） | 共通の検査をまとめて実行する仕組み。このリポジトリではrepoctlを使う。 |
| テスト用構成（fixture） | テストのために用意する入力、設定、データ、補助プログラムや資源。実環境を使うものと、動作を模すものがある。 |
| 単体・アダプターテスト | 個々の処理と、外部ツールへ接続する部分を検査するテスト。fakeやmockは外部の動作を模すため、実環境での成功とは区別する。 |
| ネイティブ実行（native） | 検証対象のOSでプログラムを実際に動かすこと。 |
| クロスビルド（cross-build） | 別のOSやCPU向けの実行ファイルを作ること。作成先の環境で動かした証拠ではない。 |
| smokeテスト | 配布候補を実際に起動し、基本動作を確認するテスト。 |
| リース・ランタイム・コンポーネント | リースは管理対象の環境、ランタイムはプロセスやComposeなどの実行資源、コンポーネントはマニフェストで宣言する機能単位。 |
| マニフェスト・worktree | マニフェストは環境の構成を宣言する設定。worktreeはGitが管理するソースの作業ディレクトリ。 |
| ダイジェスト・チェックサム | ファイル内容から計算する照合用の値。内容の変更や不一致を検出するために使う。 |
| raceテスト | 並行処理が共有データへ安全にアクセスしているかを、実行した経路で検査するテスト。 |
| 不変条件 | 処理順序や入力が変わっても守るべき条件。各テストがすべての実行順序を証明するとは限らない。 |

## 正式な検査

```text
go run ./tools/repoctl doctor
go run ./tools/repoctl check
go run ./tools/repoctl test-integration
```

`doctor`はGo、gofmt、Gitの場所を確認します。Dockerが必要なのは明示的な統合コマンドだけです。
個別の検査コマンドも直接実行できます。ハーネスにBash、Make、PowerShellは不要です。

`check`は実行内容を示しながら、整形確認、`go test ./...`、`go vet ./...`、文書検証、
生成物のずれ検出、アーキテクチャ検査を実行します。

| ハーネスのコマンド | 範囲 |
| --- | --- |
| `test-unit` | 通常のGoテスト。Dockerの常駐サービス（daemon）は不要 |
| `test-integration` | Dockerの常駐サービス（daemon）／Composeを確認し、統合テストの実行許可を明示し、build tagで選んだテストをキャッシュなしで実行 |
| `docs-check` | メタデータ、リンク／見出し、ローカル索引、AGENTSの長さ／パス、進行中の計画の必須構成、英語／日本語の対訳の欠落・更新漏れ |
| `generate` | 埋め込まれたDB変更用SQL（migration）からDB文書を再生成 |
| `generated-check` | 生成したDB構造の文書がmigrationと一致しなければ失敗 |
| `arch-check` | 修正方法を示す診断により、文書で定めたimportによる依存関係の制限を検査 |

DBの構造を説明するスキーマ文書は、[migrations](../migrations/001_initial.sql)配下の番号付きSQL群から生成します。手書きの説明を生成元にしません。
`AGENTENV-*`の安定した診断コードで、守るべき条件のどれに違反したかと、修正の方向を示します。
検査自体が問題を見逃さないことを確認するため、次の不正な状態を意図的に作ります。

- リンク、索引、メタデータ、計画の必須セクションを壊す。
- ソース整形、スキーマ生成、許可するimportの境界に違反させる。
- 翻訳を欠落・孤立させる、翻訳元を示すメタデータを誤らせる、ハッシュを古くする、言語別のリンク・索引を壊す。

## 製品のテスト

単体テストとアダプターテストでは、設定、ライフサイクル操作、失敗時の補償処理を確認します。
対象は次のとおりです。

- マニフェストの厳密な解析、同じ入力から同じコンポーネント・ソース識別情報が得られること、状態の変化。
- 有効期間（TTL）と自動回収（GC）の対象条件、正規化したCompose設定への方針適用。
- パスが許可範囲内に収まること、引数配列（argv）、出力中の秘密値を順次伏せる処理。
- 証拠を保存できない場合の処理と、ライフサイクル操作の失敗を受けた補償処理。これは、失敗までに行った作成などの作用を後始末する処理です。

外部コマンドの実行を模すfake runnerでは、実行ファイル、argv、作業ディレクトリ、環境変数の制御、
キャンセル、出力処理、エラーの変換を確認します。shell用のコマンド文字列は組み立てません。

SQLiteのテストは、一時的な実DBを使って次を確認します。

- Unicodeのパス、DBを開き直した場合と複数接続での動作。
- migrationを繰り返しても結果が変わらないことと、外部キーによる参照関係の制約。
- 容量・プロジェクトの予約が途中の状態を残さず一体として行われること、正規化された行の更新失敗時の取り消し。
- 保存済みのロックによる排他制御。

プロセスのテストでは、OSへ渡すargvと子プロセスのキャンセルを実行します。
OS固有の実装の検証には、対象OSで実際に動かす必要があります。

## 実Dockerのfixture

[統合テスト群](../internal/cli/integration_test.go)は、独立した一時Gitリポジトリと状態保存用ディレクトリを作り、
[小さなCompose fixture](../testdata/compose/compose.yaml)を使います。テストには、対象を選ぶ`integration` build tagと
明示的な実行許可（opt-in）の両方が必要です。ハーネスが自動で設定し、通常の単体テストではDockerコンテナーを起動しません。

次の動作をそれぞれ確認します。

- 同時に動くAPI／Dashboardリースには、選択したサービスと、その直接・間接の依存先を含めます。
  プロジェクトとworktreeを分離し、一方を削除しても他方のコンテナー・ネットワーク・ボリュームIDと、未選択の外部ボリュームを保持します。
- 元ソースにポートを宣言せず、マニフェストから動的なループバックHTTP接続先を生成します。
  バージョン付きの環境記述データと、コンポーネント別の実行中・保存済みログを取得できます。
- 手動削除したプロジェクトをdegraded（利用可能な状態からの劣化）として観測し、複数リポジトリではソース参照の上書きに従います。
- 名前付きテストは、秘密値を伏せた標準出力・標準エラー出力（stdout/stderr）・成果物と、非ゼロの終了状態を保存します。
  準備完了の確認に失敗した場合は、作成した実リソースを取り消します。
- 追跡対象ファイルを編集したworktreeは、差分の証拠を伴う明示的なforce指定までGCで削除しません。

## 翻訳の検証

継続して維持する文書は英語と日本語の`.ja.md`を対にし、内容が食い違う場合は英語を優先します。
[言語の方針](design-docs/bilingual-documentation.ja.md)に、メタデータとパスごとの例外を定めています。

`docs-check`は、英語ファイル全体の改行をCRLFからLFへ統一してSHA-256を計算し、翻訳に記録した原文ハッシュと比較します。
これによりWindowsのcheckoutでもLinux／macOSと同じ結果になります。
検査は読み取り専用で、翻訳メタデータを自動更新しません。

ハッシュの一致で分かるのは、どの原文リビジョンを確認したかだけです。翻訳の正確さは証明できません。
ハッシュの更新前に、実際の日本語文を見直してください。

文書の構成を実質的に変更する場合は、言語の方針に従い、英語と日本語をそれぞれ独立にレビューした後、
意味の一致を照合します。指摘はactive ExecPlanに記録します。機械的な検査に通るだけでは、
読みやすさや意味の維持を確認したことにはなりません。

## リリースの検証

tag と完全に一致する変更のないソースから、まだ存在しない出力パスを指定して作成します。
繰り返しビルドの比較には、それぞれ別の出力ディレクトリを使います。

```text
go run ./tools/repoctl release-build --version X.Y.Z --out <new-directory>
go run ./tools/repoctl release-check --dir <directory> --version X.Y.Z
go run ./tools/repoctl release-repeat --dir <directory> --version X.Y.Z
go run ./tools/repoctl release-smoke --dir <directory> --version X.Y.Z
```

`release-check` は他プラットフォームの実行ファイルを起動せず、6 アーカイブ一式と
Go 実行ファイルのビルド情報を静的に検査します。`release-smoke` は checkout の外へ展開し、
実行ファイルの検索パスを制限して、ホストと一致する対象だけを実行します。
状態には空白・非 ASCII 文字を含む独立した home を使います。同一ソース・同一ツールチェーンで
繰り返し作成し、実行ファイルとアーカイブのダイジェスト、チェックサム、マニフェストを比較します。
コンパイル成功をバイト列比較の代わりにしません。リリースCIのビルド環境は Go 1.27.1 に固定します。
Windows/macOS/Linux のネイティブsmoke 結果と arm64 の検証範囲は、
[リリース計画](exec-plans/completed/standalone-release-finalization.ja.md)に明記します。

### 公開の条件

Git tagを対象とするワークフローは、以下をすべて満たしてから公開します。

| 項目 | 必要な確認 | 確認する理由 |
| --- | --- | --- |
| リポジトリの検査 | 公開前にリポジトリハーネスとrace テストが成功する。 | リポジトリのテストや不変条件の検査が失敗しても、配布物の作成自体は成功し得るため。 |
| 成果物の静的検査 | `release-check`でアーカイブの内容、チェックサム、実行ファイルのビルドの識別情報を検証する。 | 別プラットフォームの実行ファイルを動かさずに、配布物の不正や不一致を検出するため。 |
| 繰り返しビルドの比較 | `release-repeat`で同じcommit・ツールチェーンから再ビルドし、出力のバイト列を比較する。 | ビルドが成功するだけでは、同じ配布物を再現できるとは分からないため。 |
| ネイティブsmoke テスト | 候補を展開し、Windows・macOS・Linuxで実行する。 | クロスビルドでは分からない起動の不具合や、CLIが暗黙に必要とする外部ツールなどの依存を検出するため。 |
| 検証済みのファイルを公開 | 公開ジョブで再ビルドせず、検証した候補をそのままアップロードする。 | 利用者へ配るファイルと、検証に成功したファイルを同一に保つため。 |

ワークフローの存在だけでは、リリースやネイティブテストの成功を証明しません。

### 繰り返しビルドと専用preview

`release-repeat` は tag に対応する候補を検証し、同じコミット・ツールチェーンで再ビルドして、
出力 8 ファイルすべてのバイト列を比較します。tag のないブランチや PR の検証には
専用のプレビュー を使います。

```text
go run ./tools/repoctl release-verify --out <new-directory>
go run ./tools/repoctl release-preview-smoke --dir <directory>
```

`release-verify` は変更のないソースを要求し、専用のclone（複製リポジトリ） 内だけに `v0.1.0` を作成して
2 回のビルド、バイト列比較、ローカルのネイティブsmoke を実行した後、候補を新規出力先へコピーします。
`release-preview-smoke` は別の専用のclone（複製リポジトリ） で、プレビューを現在のコミットと照合します。
どちらも公開するGit参照（ref） の作成やリリース公開は行いません。プレビュー用ワークフローはこの比較と
3 OS のネイティブsmoke ジョブを実行します。Git tagを対象とするワークフローは公開前に、独立して繰り返しビルドと
3 OS のネイティブsmoke の成功を要求します。これはワークフローの条件であり、
個別の実行が成功したという主張ではありません。

## 常駐processの検証

[process ExecPlan](exec-plans/completed/persistent-process-runtime.ja.md)で直接の受け入れ証拠を追跡します。

設定のテストでは、ランタイムを操作する前にマニフェストを検査します。

| 項目 | テストで確認すること | 確認する理由 |
| --- | --- | --- |
| ランタイムごとの設定項目 | プロセス・Compose・Androidそれぞれで許可された項目を受け入れ、別ランタイム専用の項目を拒否する。 | 適用できない設定が、気付かないまま無視されることを防ぐため。 |
| YAMLのnull・空値・merge | 値がnullや空でも、YAMLのmerge経由でも、項目が指定されたことを検査する。 | 書き方を変えるだけで、許可されない設定項目の検査をすり抜けないため。 |
| 名前付きTCPポートと準備完了の確認先 | 名前付きポートを設定する場合はTCPを要求し、準備完了を確認する接続先の参照は同じコンポーネントで宣言した接続先だけに解決する。 | 未定義のポートや別コンポーネントの接続先で、誤って準備完了を判定しないため。 |
| ディレクトリ名にも使うランタイム名 | 予約名や末尾のドットなど、対応OSでディレクトリ名に使えないプロセスランタイム名を拒否する。 | あるOSで通る設定が、別OSではディレクトリ名の制約で失敗することを防ぐため。 |
| 既存の設定スナップショットとの互換性 | プロセス用項目を追加しても、既存ランタイム設定の正規化した保存形式を変えない。 | 以前に保存した設定スナップショットとの互換性を維持するため。 |

アダプターのテストでは、検証済みの設定を使ったプロセス操作と、保存する証拠を確認します。

| 項目 | テストで確認すること | 確認する理由 |
| --- | --- | --- |
| 実行ファイルと作業ディレクトリの解決 | ソース相対の実行ファイルパスと作業ディレクトリをソース内に限定する。PATHから選ぶホスト実行ファイルも実体を確定する。 | 意図しない実行ファイルや、宣言したソース外の作業場所を使わないため。 |
| 引数・環境変数の展開 | 状態ディレクトリ、リース、ポート、環境変数の参照を実行時の値へ展開し、保存スナップショットには秘密値そのものを入れない。 | プロセスへ意図した値を渡しつつ、設定スナップショットに秘密値を残さないため。 |
| 専用状態と起動したプロセスの識別 | ランタイム専用の状態、所有記録、起動したプロセスの識別情報を検査する。 | 別のリースやランタイムの状態・プロセスを取り違えないため。 |

## 証拠の種類とテストアーキテクチャ

証拠は何を示すかで分類します。回数を増やしても証拠の種類は変わらず、反復は決定的な再現の代わりになりません。受け入れの主張ごとにリビジョン・コマンド・環境・結果・限界を記録します。

| 種類 | 示せること | 示せないこと |
| --- | --- | --- |
| 不変条件の強制検証 | 待ち合わせ点や状態の変化を使って問題の順序・境界を再現し、失敗原因を区別できる判定基準（oracle）で条件を確認 | 起こり得るすべての処理順序や実OSの挙動 |
| ネイティブ・統合テストの直接観測 | 前提条件を満たした指定ホストで実プロセス・プロトコル・エンジンの挙動を確認 | 別OSや未使用の基盤 |
| race・静的検査・ツール | 実行した経路や構造規則で問題が報告されなかった | すべての実行順序、判定基準自体の正しさ、翻訳の意味一致 |
| 安定性・反復 | 記録した回数・CPU設定で観測した安定性 | 決定的な再現や回数による証明の強化 |
| コンパイル・構造 | 型・importによる依存関係・生成物・対象プラットフォームのビルド検査への適合 | ネイティブ実行やランタイム受け入れの完了 |

種類は異なる主張を表し、上位の証拠で置換できる順位ではありません。一つのテストが複数種類の証拠を持つ場合も、それぞれ区別します。

### fixtureの所有と実行順序

テスト用補助処理ごとに、誰が管理するか、使う資源、並行処理（goroutineやコールバック）、共有状態、
完了通知、後始末の順序、失敗時の出口、呼び出す箇所、前提を記録します。
後始末では、新しい処理の受付を止め、必要に応じてキャンセルを要求したり通信接続を閉じたりします。
管理する処理が実際に終了するまで待ってから、DBや一時状態を破棄します。この終了待ちをjoinと呼びます。

停止の要求や接続のcloseだけでは、処理の完了を確認できません。

- 接続を受け付けるlistenerを閉じても、受付済みの接続は閉じません。
- HTTPサーバーを閉じても、HTTPの管理から切り離されたWebSocket（hijack）のコールバックの終了までは待ちません。
- キャンセルは終了の要求であり、終了待ちのjoinとは異なります。

ワーカーが生存を知らせる定期通知（heartbeat）など、期限のある前提条件は準備から対象操作まで有効でなければなりません。登録が成功しても、その後も利用できるとは限りません。この種のテストでは、期限切れと更新を意図的に発生させて確認します。

結果の成否判定（assertion）より先に、失敗時の後始末を登録します。実OSの資源が残り得る後始末の失敗は無視しません。
並行処理の待ち合わせと、そのテストでは次を守ります。

- WaitGroupへ処理を登録してからWaitで待ちます。カウンターをアトミック操作で保護しても、処理完了の順序は別途確認する必要があります。
- 終了を待たれる処理自身から、その終了を待ってはいけません。
- timeoutは失敗した検査の待ち時間を制限するだけです。コールバックの開始、後始末の完了、副作用がないことの証拠にはなりません。
- キャンセルの通知を確認しただけでは、後始末のgoroutineが終了待ちまで進んだとは分かりません。
- 処理間で通知を渡すchannelだけで処理順序を制御し、後始末がまだ終わっていないことを確認するテストでは、`testing/synctest`で処理が待機状態へ落ち着いてから判定します。

処理順序の制御には、適切な箇所でchannel、待ち合わせ点（barrier）、`testing/synctest`を使います。
実socketやネイティブプロセスを組み合わせて動かした証拠は、この種の順序制御による証拠と区別します。

### oracle・指摘・予防検査

ここでいうoracleは、テスト結果が期待どおりかを判断する基準です。拒否やエラーを確認するテストでは、
目的の処理へ進む前に、別の理由で拒否されても成否判定を満たしてしまい得る経路を調べ、
そのうち最も早く拒否に至る経路を特定します。
意図した変更や境界へ実際に到達することを必須とし、特定のエラーや状態を確認します。
必要に応じて、近い条件の正常な入力も試し、受け入れられることを確認します。

失敗原因と完了の証拠は、次のように区別します。

- 返されたエラー自体を確認します。contextの状態だけで操作の失敗原因を判断しません。
- 時間をおいて作成される予定のファイルが見当たらないだけでは、プロセスの終了を独立して証明できません。
- 期待値を検査対象の実装と同じロジックで計算せず、保存された状態や副作用を独立して比較します。

修正前に、各指摘のID、違反した不変条件、最初に検出できた現実的な機会、見逃した理由の分類を記録します。
テストと製品実装のどちらに問題があるか、同種の箇所にも影響するか、ACCEPT/REJECT/DEFER（採用・不採用・保留）の判断と理由も残します。
採用した修正では、可能なら同じ判定基準で修正前に失敗し、修正後に成功することを示します。
新しいテスト用APIが修正前には存在せずコンパイルできない、という失敗は不具合の再現に数えません。
ネイティブ環境で修正前後を比較できなければ、その未実施を明記します。

安定したライフサイクルや境界の条件には、対象を絞った回帰テストを優先します。
ここで回帰テストとは、変更後も既存の動作を壊していないかを確かめるテストです。
修正した不具合については、同じ問題の再発も検出します。
既存の`check`とネイティブ/race CIで実行し、別のpolicy実行ツールを増やしません。

テスト名、文章、sleepの使用、成功回数だけで証拠の品質を機械判定しません。文脈を踏まえてレビューします。
独立レビューでは、差分、テストが目的の処理へ到達するか、指摘への判断、実際の証拠を確認します。
英語・日本語それぞれの読者レビューと意味の一致のレビューは、原文ハッシュの確認とは区別します。

固定のポート範囲など、同じネイティブ資源の集合を使うテスト群は、互いの分離を確認するまで一つずつ実行します。競合後に単独で再実行した結果は原因調査の証拠であり、元の失敗を取り消すものではありません。
