# リポジトリ文書を英語・日本語で維持する

[英語版（翻訳元）](bilingual-documentation.md)

このExecPlanは更新を続ける文書であり、`docs/PLANS.md`に従って保守する。

想定ブランチ：`feat/bilingual-documentation`。

## 目的 / 全体像

この作業後、`agent-env`の人が読む永続文書は英語と日本語で維持される。
英語版を文書の内容を判断する基準とし、日本語は任意の参考コピーではなく正式な保守対象の翻訳とする。
永続的な英語文書を変更する場合、同じ一貫した変更単位で日本語訳も更新する。
リポジトリの文書検査で、翻訳の欠落と更新漏れを検出する。
初回の移行では、既存MVPとPR #2で提供したAndroid Emulator機能の日本語文書も揃える。

## 範囲

対象：

- リポジトリの二言語文書方針を定める。
- 英語／日本語のファイル名とリンク規約を定める。
- 既存の永続的な人向け文書の日本語訳を追加する。
- Android Emulatorの製品仕様と設計の日本語訳を追加する。
- リポジトリ索引で両言語を案内する。
- 将来のcoding agentが両言語を維持するよう`AGENTS.md`を更新する。
- 関連するExecPlanの完了に文書同期を要求するよう`docs/PLANS.md`を更新する。
- `repoctl docs-check`で欠落した対訳を検出する。
- 文書検証で日本語訳の更新漏れを検出する。
- 明示的な例外を文書化する。
- Windows、macOS、Linuxのリポジトリハーネス動作を検証する。

対象外：

- 別途根拠がない限り、生成されたDB／schema出力の翻訳。
- 過去のhandoff／参考資料アーカイブの翻訳。
- ソースコードのコメントの翻訳。
- CLI出力とエラーメッセージの翻訳。
- 第三者の引用文の翻訳。

## 文書モデル

翻訳元は英語ファイルのパスで指定する。

```text
README.md
ARCHITECTURE.md
docs/product-specs/android-emulator.md
```

日本語訳は`.ja.md`を使う。

```text
README.ja.md
ARCHITECTURE.ja.md
docs/product-specs/android-emulator.ja.md
```

日本語文書は翻訳元の英語文書を明示する。両言語が食い違う場合は、翻訳が直るまでは英語版の内容に従う。この不一致は文書のずれであり、意図的に作ってはならない。

## 作業計画

### 節目1 — 言語契約の定義

内容の判断基準とする言語、翻訳の命名、必須の文書分類、明示的な例外、翻訳のずれの意味、索引／リンクの動作を定める。`AGENTS.md`と`docs/PLANS.md`を更新する。

### 節目2 — 機械的な検証の追加

`repoctl docs-check`を拡張し、次のいずれかに該当する場合は検査を失敗させる。

- 必須の英語文書に日本語版がない。
- 日本語文書に対応する英語の翻訳元がない。
- メタデータが誤った翻訳元を指している。
- 記録した翻訳状態から翻訳元の英語文書が変更されている。
- 索引に壊れた言語リンクがある。

検査はBash、Make、PowerShell、symlink、CGOなしで動作すること。

### 節目3 — 既存の永続文書の翻訳

MVPとAndroid Emulatorの製品／設計契約を含む、現在の永続文書の日本語版を作る。訳すことで精度が落ちる専門用語は原語を保つ。コマンド、識別子、schema field、ファイル名、診断コード、API名は変更しない。

### 節目4 — 索引と案内の統合

有用な場所で英語文書から日本語版へリンクし、日本語版から翻訳元の英語文書へ戻れるようにする。索引は内容の判断基準を英語版に統一したまま、両言語を案内する。

### 節目5 — 受け入れと回帰検証

```text
go run ./tools/repoctl docs-check
go run ./tools/repoctl check
```

欠落した日本語訳や古い日本語訳で検証が失敗することを、不正fixtureで証明する。Windows、macOS、LinuxのネイティブCIでハーネスを検証する。

## 検証と受け入れ

A1. 必須の永続的な英語文書すべてに日本語版がある。

A2. 日本語版はそれぞれ実在する翻訳元の英語文書を示す。

A3. 日本語を同期せず英語を変更すると`repoctl docs-check`が失敗する。

A4. 両文書を更新すると同じ検査が通る。

A5. Android Emulatorの製品／設計文書が両言語で利用できる。

A6. アーキテクチャ、信頼性、セキュリティ、移植性、品質の文書が両言語で利用できる。

A7. `AGENTS.md`が永続文書の二言語保守を明示的に要求する。

A8. `docs/PLANS.md`が関連ExecPlanの完了に両言語の文書を要求する。

A9. 生成物と過去の参考資料の例外が明示され、テストされている。

A10. ハーネス全体とネイティブCIが通る。

## 冪等性と復旧

翻訳検査は決定的かつ読み取り専用であること。メタデータの自動更新を導入する場合も、通常の検査で人が読む文書を黙って書き換えてはならない。

移行失敗時に未翻訳文書が残る場合は、validatorが個別に報告する。どちらの言語の文書も削除・上書きしてはならない。

## 成果物と注記

移行した文書数、意図的に除外した文書数、翻訳の鮮度／欠落の不正fixture、ネイティブCIの証拠を記録する。

## インターフェースと依存

ハーネスの想定する窓口：

```text
repoctl docs-check
```

実装で文書メタデータの内部helperを追加してよいが、外部翻訳サービスやネットワーク接続を必須にしてはならない。
翻訳自体はcoding agentが作成してよいが、リポジトリの正しさを特定のLLMや翻訳providerへ依存させてはならない。

実装の区切り（2026-09-08）：翻訳の鮮度には、翻訳元の英語ファイル全体についてCRLFをLFへ正規化したSHA-256を使う。hashの一致は原文リビジョンを記録するだけで、意味の正確な翻訳を証明するものではない。人／agentによるレビューは引き続き必要である。パスを厳密に指定した例外は`docs/translation-exceptions.json`で管理する。新しい完了済み計画にも日本語版を維持する。通常の検査は読み取り専用である。

発見（2026-09-08）：`docs/RELIABILITY.md`にレビュー修正前のCompose inventory条件が残っていた。その1文をマージ済みPR #2に合わせて直し、正しい挙動を翻訳した。runtimeの動作変更はない。初回の翻訳検査は日本語文書の欠落、未記入hash、last_verifiedの不一致を正しく報告した。これらは移行途中の作業であり、検証を緩めて解消しない。

翻訳の区切り（2026-09-08）：必須29文書すべてに全文の日本語版を揃え、6件の厳密な例外で生成物／歴史的資料を保護した。独立レビューで精度に関する4点を修正した。具体的には、ExecPlanが作業ブランチと作業内容の判断基準であることを、操作権限と混同しないようにした。Jobの終了／永続化に根拠のない順序を導入せず、期限更新は常に延長とは限らないことを明確にした。Docker不要の説明は、個別のAndroidのみのleaseを対象とすることも明確にした。コマンド／inline識別子と、安全・検証上の制約も突き合わせた。
